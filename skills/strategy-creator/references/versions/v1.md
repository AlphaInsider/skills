## 1.0.0

### Upgrade requirements

This release introduces the shared `contract_version` marker and generated
project version-maintenance guidance. For a legacy `0.0.0` project, add the
marker to `docs/plan.md` and add the installed-version workflow to an
attributable `AGENTS.md` as part of the combined target upgrade. This increment
does not require runtime-code, test, dependency, or generated `README.md`
changes.

### Verification

Confirm that the final plan uses the installed target version and that the
generated project guidance preserves the marker until the complete approved
upgrade passes.

## 1.1.0

### Upgrade requirements

This release adds the AlphaInsider target-source, creation, access,
description, and synchronization fields to `docs/plan.md`. It also adds the
documented API-permission bundle and remote-description maintenance rules to
attributable `README.md` and `AGENTS.md` files.

For a version-only upgrade, classify the configured target as an existing
strategy, preserve its remote metadata, and do not create a strategy or sync
its description. Remote description synchronization begins only after the
user confirms a behavior plan containing the exact description. The upgrade
alone does not require runtime-code or dependency changes.

### Verification

Confirm that the plan and attributable documentation contain the installed
target-management contract. Confirm that a version-only upgrade neither
created a strategy nor synchronized its remote description.

## 1.2.0

### Upgrade requirements

This release adds the optional continuous WebSocket recovery contract without
adding plan fields. For a project that uses WebSockets, audit the existing
confirmed retry and recovery behavior before changing runtime code. Pass
`reconnect=True` to `stream_events` when the plan requires continuous
reconnection and re-subscription; retain the default one-session behavior when
the plan requires the strategy to stop on a stream error. If the existing plan
does not decide between those behaviors, return it to `draft` and confirm that
missing decision before implementation.

Projects that do not use WebSockets need no runtime change for this increment.
For WebSocket projects, inventory replacement of the copied
`strategy/alphainsider_stream.py` and any caller change under the combined
target audit. The current complete-plan confirmation governs those recorded
actions.

### Verification

Confirm that the helper, caller, documentation, and tests match the confirmed
recovery behavior before advancing `contract_version`.

## 1.3.0

### Upgrade requirements

This release moves AlphaInsider forward-test setup after strategy design and
before backtesting. It adds `## Market and instruments`, moves the existing
asset-class and instrument-selection fields there, places
`## AlphaInsider target` after `## Execution and risk`, and adds target
readiness and a non-secret deferred-reason field.

Reorder an existing plan and move its recorded fields without re-interviewing
settled decisions. Mark an already complete, compatible target `ready`. If
target setup cannot complete, record `deferred` and its non-secret reason;
preserve all unaffected strategy and backtesting decisions. Update an
attributable `AGENTS.md` with the deferred-target remote-work gate. When the
generated `README.md` describes operational commands for a deferred target,
mark those commands unavailable until the plan is reconfirmed with a ready
target.

A confirmed deferred plan may retain or receive a complete local implementation
with mocked external interactions, but it makes no remote calls and remains
`confirmed`. Resume by returning the plan to `draft`, resolving only target
gaps, and reconfirming the complete plan. This increment alone does not require
runtime-code or dependency changes for a ready target and never creates or
synchronizes a remote strategy during a version-only upgrade.

### Verification

Confirm the new section order, preserved field values, explicit target
readiness, and updated attributable agent guidance. For a deferred target,
confirm that operational commands are marked unavailable, external calls stay
mocked, and the plan cannot become `implemented`. For a ready target, confirm
that a version-only upgrade neither creates a strategy nor synchronizes its
remote description before advancing `contract_version`.

## 1.3.1

### Upgrade requirements

This release removes the separate draft-stage core-creation approval. Remove
`Core creation fields approval` from `docs/plan.md` without re-interviewing or
changing the recorded type, name, owner starting balance, access mode, price,
or description. Complete plan confirmation is the sole authorization to call
`newStrategy` with those exact fields and persist its returned ID.

Audit the generated one-cycle and continuous commands for an interactive
confirmation before planned paper orders. Remove that prompt while preserving
all signal, risk, reconciliation, and order behavior. Running either command is
the user's execution action; the upgrade and build workflows never start a
command automatically. Reflect this contract in attributable `README.md` and
`AGENTS.md` files. Preserve settled target-selection, credential, overwrite,
replacement-deletion, and failed-creation-cleanup decisions.

### Verification

Confirm that planning reaches one complete plan confirmation without a
separate core-creation approval, then creates only the confirmed target. Confirm
that pre-confirmation field changes update the draft and post-confirmation
changes return it to `draft`. Verify that both operational commands contain no
interactive confirmation and are never run by build or offline verification.
A version-only upgrade must not create a target or submit an order before
advancing `contract_version`.

## 1.4.0

### Upgrade requirements

This release adds `## Background operation` after `## Execution and risk` and
before `## AlphaInsider target`. Reorder existing sections without
re-interviewing settled strategy, target, backtesting, or implementation
decisions. Return the plan to `draft` and ask only whether the continuous
command should remain foreground-only or use a supported background manager,
plus the dependent manager, identifier, login-autostart, supported restart,
retry, and log-exposure decisions.

This release also makes final complete-plan confirmation the only skill-level
execution approval. Before confirmation, inventory and resolve every exact
create, modify, overwrite, delete, stop, disable, promotion, provisioning,
synchronization, ID-persistence, and host-install action. Replacement plans
must contain their complete deletion and promotion inventory. For a target not
yet created, record whether the exact target created by the current run should
be retained or deleted if later work fails. The final confirmation authorizes
all recorded implementation, update, replacement, and conditional-cleanup
actions without another prompt.

For background operation, use only an available systemd user unit, launchd user
agent, or manual-only tmux session. Do not install dependencies or configure
system-wide, pre-login, lingering, or Windows services. Add the selected
manager's lifecycle and management instructions to attributable `README.md`
and preserve its host-write, credential, collision, inactive-install, and
no-automatic-start rules in attributable `AGENTS.md`.

A version-only audit is read-only and creates no separate approval gate. Return
the plan to `draft`, preserve settled decisions, record the complete upgrade
inventory, and obtain one final complete-plan confirmation before any write. If
an unplanned path or action appears later, return to `draft` and reconfirm the
complete plan instead of requesting a one-off approval. A confirmed ready plan
may install its exact user-level native definition after
the normal build, verification, and remote synchronization gates, but never
starts a new or replacement strategy. A deferred target retains normalized
background decisions and installs nothing. If required installation fails,
leave the plan `confirmed`. For a runtime-affecting update to an attributable
running service, disclose stop and disable behavior in the reconfirmed plan,
then leave it stopped and report the user-run resume command.

### Verification

Confirm the new plan and interview order, preserved `1.3.1` decisions, and all
foreground, systemd, launchd, and tmux branches. Verify manager limitations,
log choices, inactive installation, deferred-target behavior, collisions, and
stop-without-restart maintenance. Confirm one final approval covers planned
overwrites, replacements, remote work, background installation, update stops,
and the failed-current-run cleanup policy. Mock manager operations; never start
a background process or submit an AlphaInsider order during upgrade or tests.

## 1.6.0

### Upgrade requirements

This release replaces `## Background operation` with `## Operation and
scheduling`. Continuous operation now describes either a persistent process or
recurring finite cycles, while a single run executes one cycle. Reorder the
plan and interview without changing the surrounding `1.5.1` phase order, then
replace the legacy background fields with operation mode, invocation model,
cadence and runtime, capability, resource identity, missed-run acceptance,
activation, overlap and retry, observability, and installation fields.

Offer foreground for a single run or persistent visible process. Offer a
compatible native user-system runner before an agent scheduled task: systemd
and launchd may run persistent processes or recurring finite cycles, Windows
Task Scheduler may run recurring finite cycles only, and each agent-task
occurrence runs the exact finite one-cycle command once. Agent tasks may use a
local project or an already prepared remote or web runtime, but the upgrade
never provisions remote infrastructure or reconstructs a strategy from chat.

Every recurring runner must fit the confirmed cadence and worst-case cycle
duration, prevent overlap, disable scheduler-level retry, disclose missed-run
behavior for acceptance, and avoid credentials in definitions and prompts.
Record active or inactive installation, recommending inactive, and never
trigger an immediate run. Active confirmation authorizes only the recorded
future occurrences or next-login startup.

Map a legacy `foreground only` continuous-command plan to `foreground` plus
`persistent process`. Map an existing systemd or launchd plan to `native
user-system` plus `persistent process`, preserving its attributable identity,
autostart, persistent-service restart, logging, installation state, and every
unrelated strategy decision. Normalize recurring-only fields as not
applicable. A legacy tmux plan cannot be migrated because tmux is no longer a
supported runner: return it to `draft` and interview only Operation and
scheduling and affected dependents. Preserve all other settled values.

This release also adds explicit cleanup and retirement without adding a
Strategy Plan interview phase. Add managed-artifact retirement, operation
cleanup, and target lifecycle fields with `not initiated` values; ask no new
strategy question during upgrade. Recognize `retired` as a non-operational
audit status and stage one explicit retirement or outgoing replacement in
`docs/cleanup-plan.md`, which uses only `draft` or `confirmed` and is the sole
plan permitted to record the exact non-secret AlphaInsider strategy ID.

For an explicit cleanup, require exact project, artifact, runner, process, and
target attribution. Ask whether the verified owned target should be retained
and detached or deleted; both Strategy Creator-created and selected existing
owned targets are eligible. Disable future operation first, wait for active
cycles, gracefully stop persistent processes, remove only exact attributable
resources, and preserve `.env`, `.gitignore`, credentials, caches, historical
data, unrelated files, and uncertain resources. Deletion preflight records
subscriber, open-order, and nonzero-position findings and warns that
`deleteStrategy` documents no cascade behavior; it never cancels orders,
liquidates positions, or submits a trade.

A replacement prepares its outgoing cleanup plan while draft, waits for the
replacement target to become ready, then applies cleanup and archives the old
plan at `docs/retired/YYYYMMDDTHHMMSSZ-<slug>.md` before promotion. A deferred
replacement leaves the outgoing strategy untouched. Remote deletion failure
retains the confirmed cleanup plan and permits a ready replacement's confirmed
future activation with a warning; shutdown, operation-removal, archive,
promotion, or local-cleanup failure blocks activation. Cleanup never retries
during unrelated work.

A version-only upgrade records the new section and compatible field mappings
and derived cleanup fields, then advances `contract_version` only after final
confirmation. It creates no cleanup plan and performs no remote,
native-manager, agent-scheduler, background-process, or trading action and no
cleanup action. A deferred target creates no operation resource. Runtime changes needed
for a newly selected recurring model occur only after its complete updated plan
is confirmed.

### Verification

Confirm the exact plan and interview order, all foreground, native persistent,
native recurring, local agent, and remote or web agent branches, and omission
of incompatible runners. Verify one finite cycle per scheduled occurrence,
indefinite recurrence until paused or deleted, non-overlap, disabled scheduler
retry, missed-run acceptance, failure-only notification defaults, active and
inactive installation, no immediate run, deferred-target behavior, collision
handling, and pause-without-resume maintenance.

Verify automatic migration for foreground, systemd, and launchd plans and
Operation-and-scheduling-only re-interview for tmux plans. Confirm every
unrelated strategy decision remains unchanged and the upgrade itself creates,
updates, pauses, disables, starts, or deletes no operational resource.

Verify explicit retirement and replacement cleanup for foreground, native
persistent, native recurring, and local or remote agent-task operation. Cover
exact attribution, safe-cycle waiting, selected-existing owned-target deletion,
retain-and-detach behavior, live-state warnings, target and ownership mismatch,
deletion failure, retired records, archive collisions, stale runtime locks, and
unavailable task capabilities. Confirm no path cancels an order, liquidates a
position, submits a trade, triggers an immediate run, or retries cleanup during
unrelated work.
